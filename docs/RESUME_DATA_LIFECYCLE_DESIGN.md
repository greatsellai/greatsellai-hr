# 候选人数据生命周期设计

**版本：** V1.0
**日期：** 2026-07-21
**状态：** 待确认，确认后实施
**关联：** [全版本 PRD](PRD_ALL_VERSIONS.md)、[实施计划](IMPLEMENTATION_PLAN.md)、[多命名收件邮箱 PRD](MULTI_NAMED_MAILBOX_PRD.md)

## 1. 背景与目标

现有“邮箱保留策略”只清理 `MailboxContentReplica` 中的邮件正文、失败附件等临时副本，明确不会触碰已入库的候选人原文件、解析文本、结构化事实、评分、总结或 JD 匹配结果。本设计补齐候选人数据本体的完整生命周期：

1. 对原文件的服务器授权预览和下载留下可追溯审计；
2. 支持按单份简历或整位候选人发起删除，并立即撤销业务访问；
3. 支持管理员按当前工作区安全导出候选人数据；
4. 支持工作区配置简历保留期限、预览到期影响，并由后台可重试地清理；
5. 保持现有工作区隔离、原件路径隔离、AI 证据约束和“不得自动作出招聘决定”的边界。

本设计不复用邮箱副本保留表或任务表，也不让平台管理员绕过工作区读取候选人内容。

## 2. 当前缺口

- 原文件仅有受会话和工作区保护的 inline 查看入口；没有区分预览与下载，也没有访问审计。
- 候选人和简历没有删除、恢复、物理清理、导出或本体保留期限。直接删除 `Resume` 会被评分、总结、JD 匹配、批次任务、邮箱附件记录等外键和来源关系阻断。
- 邮箱保留只处理临时缓存；其路径解析刻意排除了 `Resume.storage_key`，不能作为候选人简历清理器。

## 3. 不可变业务规则

1. 所有读、写、后台任务、导出件和原文件访问均按当前 `organization_id` 隔离。跨工作区的资源 ID 统一返回 `404`。
2. 原文件、原文、姓名、文件名、邮箱地址、简历哈希、邮件主题和模型原文不得写入审计事件、任务错误、导出操作日志或 Agent 结果。
3. `admin` 可以删除、恢复、设置保留策略、执行清理和创建导出；已验证的 `admin` 与 `recruiter` 可以通过被审计的显式操作预览或下载其工作区原文件。平台管理员身份不额外获得候选人数据权限。
4. 招聘 Agent 不提供删除、恢复、导出、保留策略或原文件访问工具。
5. 删除后立即从简历库、筛选、详情、评分、总结、JD 匹配、Agent、原文件和普通 API 中消失；后台物理清理失败也不能让数据重新可见。

## 4. 原文件预览与下载审计

### 4.1 操作模型

前端不再把同一个 Blob 请求同时当作“预览”和“下载”。改为显式发起两类操作：

- `view`：在抽屉中预览原文件；
- `download`：以附件形式下载原文件。

前端先调用 `POST /v1/resumes/{resume_id}/file-access`，请求体只含 `purpose: view | download`。服务端在确认当前工作区、简历未删除、文件仍存在且操作者有权限后：

1. 追加一条候选人数据审计事件；
2. 生成一次性、短时、与当前会话绑定的访问授权；
3. 返回不含简历 ID、文件名和个人信息的读取地址。

读取地址只接受已绑定的登录会话，短时失效且不可复用；它根据授权意图返回 `inline` 或 `attachment`。这样 PDF Range 请求、iframe 重试或浏览器自动重载不会被误记为多次人工查看。审计语义固定为“服务器已授权并开始响应”，不声称能够证明用户已完整阅读或保存文件。

为兼容旧客户端，现有 `/v1/resumes/{resume_id}/original-file` 在一个兼容发布周期内仅作为被审计的 `view` 入口；新前端只使用显式授权流程。兼容期结束后删除旧入口。

### 4.2 审计数据

新增追加式、工作区隔离的 `candidate_data_audit_events`。事件最少保存：工作区 ID、操作者用户 ID、动作、目标类型、候选人 ID、简历 ID、请求 ID、结果、时间和安全的来源类型。动作包括：

- `resume_original_view_authorized`
- `resume_original_download_authorized`
- `candidate_delete_requested`
- `resume_delete_requested`
- `candidate_restored`
- `resume_restored`
- `candidate_data_export_requested`
- `candidate_data_export_download_authorized`
- `retention_policy_changed`
- `retention_cleanup_completed`
- `candidate_data_purged`

审计事件不保存文件名、存储路径、原文、姓名、邮件元数据、AI 输出、密钥或请求体。审计写入失败时，原文件授权与导出下载失败关闭，避免产生未记录的数据访问。

## 5. 删除、恢复与物理清理

### 5.1 两阶段删除

删除不会在网页请求中直接删除文件或数据库行。请求只完成逻辑删除和撤销访问，后台清理器负责最终物理删除。

- `DELETE /v1/resumes/{resume_id}`：删除单个简历版本；同一候选人的其他版本保持不变。若删除当前激活版本，系统只在存在其他 `ready` 且未删除版本时原子地切换到最新版本；否则该候选人没有可用简历。
- `DELETE /v1/candidates/{candidate_id}`：以同一个删除批次逻辑删除候选人及其全部简历版本。
- 两个接口都要求管理员确认原因：`candidate_request`、`recruitment_closed`、`duplicate`、`retention_expired` 或 `other`。`other` 必填简短说明，说明不写入公开响应或 AI 上下文。

逻辑删除完成后立即返回 `202` 与删除批次、恢复截止时间和预计清理时间。默认保留 7 天恢复窗口；恢复只恢复同一删除批次影响的对象，避免候选人恢复时误恢复此前单独删除的旧版本。恢复截止后只能由后台物理清理，普通前端没有“立即绕过清理”的入口。

### 5.2 状态与并发

`Candidate` 与 `Resume` 增加生命周期字段：`deleted_at`、`deleted_by_user_id`、`deletion_batch_id`、`purge_after_at`、`retention_hold`。默认查询条件排除 `deleted_at IS NOT NULL`；受控 worker、恢复和审计服务使用显式生命周期 bypass，不能依赖普通业务查询读取已删除记录。

新增 `candidate_data_deletion_batches` 和带租约的 `candidate_data_purge_jobs`。任务状态为 `queued`、`running`、`retryable_failed`、`completed`；同一删除批次一次只允许一个 worker 领取。删除事务先取消或失效该对象的 AI 提取、评分和 JD 匹配待处理项；各 worker 在写回前再次检查生命周期状态，不能在删除后重新生成任何结果。

### 5.3 物理删除范围

清理器对一个批次按工作区运行，并以幂等步骤处理：

1. 再次确认删除批次到期、无保留冻结且对象仍处于删除状态；
2. 断开或删除所有简历派生数据：原文块、教育/经历/技能、事实快照、总结、评分、评分批次项、JD 匹配、JD 匹配批次项、AI 提取任务、上传幂等键和简历复核记录；
3. 将邮箱附件审计与该简历脱钩，并清理仍存在的对应邮件副本。附件文件名、邮件标识等可关联候选人的字段按删除策略脱敏；邮件入库保留工作区级 HMAC tombstone，防止同一已删除附件因轮询或重试自动重建候选人，但不阻止管理员后续明确的手工重新上传；
4. 在工作区受限路径内删除原文件。文件删除失败时保持逻辑删除、记录安全错误码并重试；
5. 删除简历与没有剩余版本的候选人；保留仅含不透明 ID、时间、动作和计数的审计 tombstone。

任务不会删除邮箱配置、其他候选人、JD、评分模板、平台用量账本或工作区本身。

## 6. 简历保留期限与清理策略

### 6.1 工作区策略

新增每工作区一条 `candidate_data_retention_policies`。初始迁移默认为 `manual`，不会因上线自动删除既有简历。管理员可以启用自动策略，并从 90、180、365、730 天或 30–3650 天自定义天数中选择；界面默认推荐 365 天。

到期锚点取候选人最近一次已入库简历的上传/收件时间，或管理员显式批准的延期时间。浏览、下载、AI 重试、评分和 JD 匹配都不会续期，避免一次阅读让数据无限期留存。管理员可对个别候选人添加或取消保留冻结，必须填写原因并记审计。

修改策略前必须调用预览接口，显示会进入逻辑删除、会在恢复期后物理清理、被保留冻结跳过和无法处理的数量。只有管理员明确确认预览版本后，策略才生效；已过期的既有数据不会在未确认预览的情况下被突然清理。策略默认只作用于后续新入库数据；若管理员希望追溯已有简历，必须在同一次确认中显式选择并再次预览。

### 6.2 后台执行

- `POST /v1/candidate-data/retention/preview`：无副作用预览。
- `GET /v1/candidate-data/retention` 与 `PUT /v1/candidate-data/retention`：查看和更新当前工作区策略。
- `POST /v1/candidate-data/retention/cleanup`：管理员请求一次后台清理，不在 HTTP 请求中遍历或删文件。
- `GET /v1/candidate-data/retention/runs`：查看当前工作区仅含计数、状态、错误码和时间的运行记录。

现有 worker 增加独立的生命周期调度循环；每次按小批次、租约和工作区上下文执行。运行记录保存扫描数、逻辑删除数、物理清理数、跳过数、失败数和回收字节数，不保存候选人身份信息。失败会重试并产生工作区内可见的安全告警，不会静默遗漏。

## 7. 数据导出

导出是管理员专用的异步快照任务，而不是浏览器直接批量读取数据库。

### 7.1 导出范围与内容

`POST /v1/candidate-data-exports` 接受当前工作区内的候选人 ID 列表或服务端保存的筛选快照。服务端重新验证每个对象属于当前工作区且未删除；客户端提供的其他工作区 ID 一律忽略并返回 `404`，不泄露其存在。

导出默认生成 CSV/XLSX 与 JSON“事实包”：每位候选人的结构化事实、仅本地从简历原文提取的电话/邮箱、AI 总结、评分、JD 匹配与来源版本说明，但不包含 `raw_text`、原文块或原始简历文件。联系方式只进入受当前工作区授权的候选人数据导出，不进入评分、匹配、Agent 或模型输入；联系方式的原文证据块 ID 同样不导出。CSV/XLSX 对以 `=`, `+`, `-`, `@` 开头的内容按纯文本转义，防止表格公式注入。管理员可显式选择包含原始简历文件；包含时生成 ZIP，按候选人分目录，并附 `manifest.json`，同时受数量与总体积上限控制。导出永远排除：邮箱授权码、邮件正文/临时副本、发件人地址、会话、密码、API Key、模型 Prompt/原始响应、平台控制面数据和其他工作区内容。

### 7.2 存储与下载

新增 `candidate_data_exports`，保存请求人、当前工作区、对象 ID 快照、选项、状态、租约、过期时间、输出存储键、大小和安全错误码。输出只存放在独立的工作区导出命名空间，默认 24 小时失效；下载与原文件一样必须先获取一次性、会话绑定的授权并记录审计。到期、取消或下载窗口结束后由 worker 删除导出文件和输出记录，不影响候选人原始数据。

接口包括：

- `GET /v1/candidate-data-exports`：当前工作区的导出历史；
- `POST /v1/candidate-data-exports`：创建导出任务；
- `GET /v1/candidate-data-exports/{export_id}`：查询进度与到期时间；
- `POST /v1/candidate-data-exports/{export_id}/download-access`：创建被审计的短时下载授权；
- `DELETE /v1/candidate-data-exports/{export_id}`：取消尚未完成的任务或提前清除导出件。

## 8. 前端体验

1. 简历抽屉保留“原始文件”区域，提供明确的“预览”和“下载”两个按钮；非 PDF 继续按文件类型显示可预览或下载提示。
2. 候选人/简历操作菜单仅管理员可见，删除前明确显示影响范围、恢复截止时间与原因输入；删除后显示“已删除，可在 X 前恢复”。
3. 新增“数据与保留”设置页：策略、预览结果、保留冻结、清理运行和恢复队列。邮箱副本留存仍留在邮箱页面，避免把两类数据混淆。
4. 导出中心展示任务状态、创建时间、到期时间、下载按钮和安全错误码；不在列表或通知中展示候选人姓名、文件名或原文。
5. 当前工作区管理员可查看自己的候选人数据操作日志；平台控制台不展示该日志及候选人内容。

## 9. 数据模型与迁移

迁移分为可回滚的结构升级和不破坏现有数据的初始化：

- 为 `candidates`、`resumes` 增加生命周期字段和查询索引；
- 新增候选人数据审计、文件访问授权、删除批次、清理任务、保留策略、保留运行与导出任务表；
- 为邮件导入关联增加安全脱钩/脱敏所需的可空字段或状态；
- 新增仅供邮箱去重使用的 HMAC tombstone，绝不保留裸简历哈希作为删除后的身份标记；
- 给既有工作区创建 `manual` 策略，不回填到期时间、不移动原件、不删除现存记录；
- 迁移升级测试覆盖 SQLite 和 PostgreSQL 约束、空库、已有简历、已有邮箱来源和已删除批次。

所有候选人生命周期表都直接保存 `organization_id` 并受现有 tenant scope 保护。任何需要跨工作区领取任务的 worker 只可短暂领取任务，随后必须恢复到任务所属工作区上下文再读写业务数据。

应用层物理清理只保证在线数据库、上传目录和短期导出目录不再保留该数据。生产备份、对象存储版本和灾备副本必须遵循独立的受控保留期限；产品界面与审计记录不得把在线删除表述为对所有历史备份的即时抹除。

## 10. 验收与测试

至少覆盖以下场景：

1. 同工作区的预览和下载各产生一条正确操作者与动作的审计；Range、iframe 重试不重复记为人工操作。
2. 未登录、试用过期、跨工作区、已删除或文件不存在的原件访问均不产生成功审计且不能泄露目标信息。
3. 单简历删除不影响同候选人其他版本；候选人删除覆盖全部版本；恢复只恢复同一删除批次。
4. 删除后，简历库、筛选、详情、原件、评分、总结、JD 匹配、Agent 与所有后台写回路径都不可访问或重新可见。
5. 物理文件删除失败可重试，期间始终不可公开访问；清理最终移除原文、事实和派生 AI 结果。
6. 邮箱导入关联不会残留可关联的候选人元数据，也不会因旧哈希永久阻止同内容的未来重新入库。
7. 保留预览无副作用；保留冻结、UTC 到期边界、并发租约、策略变更确认与删除竞争均正确。
8. 导出只含当前工作区且未删除的快照，默认不含原件；原件选项正确、下载被审计、过期导出件自动清除。
9. 平台管理员不能利用平台 API、审计 API、导出 ID 或文件授权读取任一工作区候选人数据。
10. 完整后端 pytest、前端生产构建、迁移升级路径、跨工作区越权回归和 `git diff --check` 全部通过。

## 11. 实施顺序

1. 先完成模型、迁移、统一的“已删除不可见”查询边界和候选人数据审计服务；
2. 接入原文件授权/审计、单简历与候选人逻辑删除、恢复和后台物理清理；
3. 实现保留策略、预览、运行记录和 worker 调度；
4. 实现异步导出、短时下载和到期清理；
5. 完成前端入口、空/错误状态、跨工作区/并发/迁移回归与 PR 审查。

设计确认前不实施业务代码、不修改生产配置或服务器。
