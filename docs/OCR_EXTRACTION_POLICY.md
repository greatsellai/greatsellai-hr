# 简历文本提取与 OCR 质量策略

本文说明当前多格式简历解析的质量边界、OCR 触发条件和运营统计口径。它是
内部实现与发布说明，不是面向招聘者的错误码说明。

## 解析与修复顺序

1. 文档 worker 先读取原生文字层或对应格式的安全文本。
2. PDF 单页的非空白字符少于 `OCR_SPARSE_TEXT_CHARS_PER_PAGE` 时，或发现已知
   Unicode 损坏信号时，先尝试 PyMuPDF 原生恢复。
3. 恢复结果仍不足或不可靠、且腾讯 OCR 已配置时，再对该页请求腾讯 OCR。
4. 只有质量更好的恢复结果才会替换当前页文本；原件始终保留在所属工作区。

默认稀疏页阈值为 **200** 个非空白字符。部署时若显式设置了
`OCR_SPARSE_TEXT_CHARS_PER_PAGE`，该环境变量仍优先于默认值；发布负责人应确认
其值符合本策略。

## 腾讯 OCR Action

`TENCENT_OCR_API` 控制扫描页和图片简历使用的腾讯 OCR Action。未设置时保持历史
`GeneralBasicOCR` 行为；需要更高识别精度时，显式设置
`TENCENT_OCR_API=GeneralAccurateOCR`。生产环境模板已选择高精度版，staging 必须
复制生产的同一值，以便在发布前验证完全相同的 OCR 路径。两种模式都仅发送进程内
Base64 图像，不会为原件创建公开 URL。

## 质量门槛

“需要尝试修复”和“不能用于 AI 结论”是两件事：

- 少量已知损坏字符会触发恢复路径，但不会仅因此阻断筛选、评分、总结或 JD 匹配。
- 在所有可用恢复路径完成后，单页非空白字符中有 **10% 或以上** 属于已知损坏
  Unicode 字符时，该页才会进入不可用状态。
- 损坏计数包括替换字符、私用区、控制/未分配字符、CJK 偏旁/笔画占位字符，以及
  典型 Latin-1 误解码模式；普通图标、版式符号和 emoji 不计入损坏比例。

这项门槛只保护 AI 结论不建立在不可靠文本上，不自动做录用或拒绝决定。已有历史
版本的质量标记不会被静默改写；需要按新策略复核时，应从原件创建新的解析版本。

## 用户提示

招聘者界面不展示技术错误码或字符损坏术语：

- 原件无法得到可用文字：`简历提取失败。请重新上传清晰、完整的原文件后重试。`
- 临时的服务器、转换器或 OCR 服务问题：`服务暂时不可用，请稍后重试。`

原始错误码仍仅保留在服务端日志、审计和受限运维入口，便于定位问题。

## OCR 使用统计

从本策略发布后的新文档解析开始，平台运行时概览会记录按 UTC 日期和粗粒度文件
类型汇总的计数：文档解析数、总页数、OCR 尝试/成功/采用/失败的文档数与页数。
表中不保存工作区、候选人、简历、文件名、路径、原文、Provider 响应或错误原文。

因此可以计算：

- OCR 尝试页占比 = OCR 尝试页数 / 总源页数；
- OCR 成功率 = OCR 成功页数 / OCR 尝试页数；
- OCR 采用率 = OCR 采用页数 / OCR 成功页数。

历史解析没有页级调用审计，不能反推出历史真实调用或计费量；统计从迁移上线后的
新解析开始累积。

这些数值用于运行诊断，不是计费账本。聚合写入异常不会阻断简历处理，并会留下受限
运维日志；生产 PostgreSQL 使用原子累加，避免并发写入丢失已成功落库的增量。
