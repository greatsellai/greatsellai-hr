# GreatSell AI 招聘工具产品需求文档

**版本：** V1.0  
**日期：** 2026-07-17  
**状态：** 产品基线  
**适用范围：** 基础版、高级版、专业版

## 1. 产品概述

GreatSell AI 是面向招聘人员的桌面端招聘工作台。它将重新上传的 PDF 简历转成有来源的结构化事实，并在此基础上提供筛选、评分、总结、JD 匹配、简历收集、JD 撰写和面试辅助能力。

产品的核心原则是：AI 用于提取、分析和组织信息，招聘决策始终由人作出。系统不得基于性别、年龄、照片、婚育、籍贯、联系方式等敏感或非岗位必要信息做筛选、评分或排序。

首期仅支持一个管理账号、中文桌面端、PDF 简历、不共享数据。生产环境部署在云服务器，模型与文件访问均只经后端完成。

## 2. 用户与使用场景

| 用户 | 主要任务 | 当前阶段 |
| --- | --- | --- |
| 招聘 HR / 用人 HR | 收集简历、筛选候选人、查看总结和评分、推进面试 | 全版本 |
| HRBP | 复核面试材料、阅读综合面试参考、给出人事建议 | 专业版 |
| 用人经理 | 提供 JD、岗位画像和面试要求，查看候选人结论 | 后续权限扩展，首期与 HR 共用账号 |

## 3. 版本与售卖边界

| 版本 | 包含能力 | 不包含能力 |
| --- | --- | --- |
| 基础版 A | 简历筛选、配置权重评分、AI 总结、JD 匹配评分、招聘 Agent | 自动收件、AI 写 JD、面试能力 |
| 高级版 B | 包含 A，加收简历邮箱自动收集、AI-JD 撰写 | 面试题与面试综合结论 |
| 专业版 C | 包含 A+B，加线上面试题、线下面试题、HRBP 面试参考 | 自动拒绝、自动邀约、自动作出录用决定 |

## 4. 全局业务流程

    简历来源（手动上传 / 高级版收件邮箱）
        → PDF 校验与文本提取
        → AI 提取带证据的简历事实
        → 简历库
        → 条件筛选 / AI 总结 / 通用评分 / JD 匹配
        → 高级版 AI-JD
        → 专业版线上、线下面试材料与 HRBP 参考

每次 AI 分析都必须记录所用简历版本、事实版本、JD 版本、评分模板版本、模型名称与创建时间。简历更新后，旧结论仍可回溯，不得被静默覆盖。

# 5. 基础版 A PRD

## A0. 基础版目标

让招聘人员在一个工作台内完成“找人、看人、评人、比人”。用户无需阅读全部原 PDF，仍可看到 AI 结论、分数、命中原因和原始简历入口。

### A0.1 输入与数据质量

- 仅接受 PDF，校验扩展名、MIME、文件头、大小和可解析性。
- 优先读取 PDF 原生文字层；首期不将 OCR 作为必经依赖。
- 页数不一致、文本过少、解析失败、AI 结构化失败的简历不得进入可筛选状态。
- AI 从简历中提取姓名、教育、工作/实习、项目、竞赛、职责明细和技能；每项必须关联原文证据块。
- 电话和邮箱仅由本地规则从简历原文块提取并保留来源；它们只在受当前工作区授权的候选人详情和数据导出中展示，不发送给模型，也不参与筛选、评分、JD 匹配、排序或招聘 Agent。
- 每条教育经历保存一个可审计的院校分类：`985`、`211`、本科、大专、中专或海外院校；同一教育经历不会同时属于 985 和 211。`211` 严格指非 985 的历史 211 院校。候选人可因多段教育经历拥有多个标签。
- `is_985_211` 只作为兼容汇总字段：任一教育经历为 985 或 211 时为 `true`，不再驱动新的筛选或展示。
- 不要求人工确认后才能入库。通过证据校验的 AI 结果自动启用；异常简历保留重试和重新上传入口。

## A1. 简历按条件筛选

### 用户目标

快速找到满足岗位硬条件的候选人，并理解每个人为什么被筛出。

### 功能需求

1. 支持组合筛选：
   - 最高学历按博士、硕士、本科、大专、高中、中专/职高及以下排列；
   - 院校类型固定按 985、211、本科、大专、中专、海外院校排列，并显示在结果表上方；
   - 学校名称支持受控全称和简称，专业支持用户自由填写；
   - 应届/往届按最高教育经历毕业年月和可配置应届窗口确定；
   - 正式工作年限、工作加实习年限；
   - 正式工作、实习、项目、科研、技能竞赛、校内组织、社团、社会实践、创业和培训经历；
   - 技能分类、自定义技能以及“全部具备/任一具备”；
   - 大学英语四/六级、雅思、托福、专业四/八级、BEC、TOEIC 等中英文证书名及可选最低分；
   - 奖学金、竞赛与获奖、成绩/GPA/排名和班级、社团、项目组、公司的领导角色；
   - 用户补充关键词的泛匹配和精准匹配。
2. 顶层条件默认为 AND；同一教育或经历记录内的条件必须在同一记录上同时命中，避免跨记录误命中。
3. 只检索当前激活且状态为 `ready` 的简历。
4. 结果列表展示候选人、教育经历归类出的院校类型、最高学历、工作年限、命中原因、AI 总结预览、最近评分和打开原文件的入口。
5. 支持保存、复用、删除筛选器。
6. 支持自然语言招聘 Agent，例如“找 985/211、3 年以上 Python 的候选人”。新的主动找人请求先生成可确认的人才画像草案；只有 HR 明确点击“开始找人”后才调用受控召回。`search_candidates` 仍用于明确的普通简历库查询。查询英语证书时，已提取证书或可靠原简历中明确提及的证书均计为“已确认（简历自述）”；原文明确写为备考或未通过时不得计为已确认；未命中只能标为“未确认”，不得表述为候选人未通过。结果须展示确认/未确认数量和简历事实或原文依据，不向招聘者暴露内部 JSON 参数。
7. 未提取到的奖学金、证书、成绩或获奖事实为“未知”，不得推断为“没有”；所有命中必须返回原文证据。
8. 历史简历可按需运行 V2 事实补充任务；任务按事实版本加锁并增量合并，不删除旧事实。

### 验收标准

- 同时设置“985”“本科专业”“Python”“36 个月工作经历”时，只返回同一教育经历满足学校/专业条件且整体满足其余条件的候选人；选择“211”不得命中 985。
- 每个结果至少展示一个可解释命中依据。
- 项目、竞赛、课程设计不得被误计为正式工作年限。

### 候选人收藏（个人私有，后续增强）

#### 目标

帮助招聘官把值得后续关注的人选暂存到个人收藏库，便于回访、横向比较或后续手动加入岗位流程。收藏不改变候选人的招聘状态、评分、JD 匹配结论或其他成员视图。

#### 核心规则

1. 收藏对象是“候选人”，不是某一份简历。同一候选人在同一用户的收藏库中只能存在一次；候选人有多份简历时，列表优先展示当前已启用版本，否则展示最新待处理版本。
2. 收藏为“工作区内、按用户私有”的标记：不同招聘官可分别收藏同一候选人；A 的收藏不得出现在 B 的收藏库、人才库标记或候选人详情中。
3. 收藏和取消收藏均必须幂等，重复操作后分别稳定为“已收藏”或“未收藏”；收藏库按收藏时间倒序并支持分页。
4. 已进入删除或清理流程的候选人不得再被收藏，也不得出现在收藏库；候选人被物理清理时，相关收藏标记必须同步物理删除。
5. 收藏不创建候选人副本，不复制简历原件、提取事实、AI 总结、评分或 JD 匹配数据；它不等同于加入岗位招聘流程、淘汰/录用阶段、团队共享人才池、标签、备注或提醒。

#### 权限、交互与验收

- 仅已登录、邮箱已验证且当前套餐有效的工作区成员可使用；所有读写同时按当前工作区和当前用户过滤，跨工作区候选人统一返回“不存在”，不得泄露其存在性。
- 不提供“谁收藏了该候选人”的接口、入口或统计；收藏状态不得进入 AI 提示词、评分、JD 匹配或任何自动决策。
- 候选人详情提供“收藏候选人 / 已收藏”切换按钮，包含加载、防重复点击和成功/失败反馈；左侧导航提供“收藏库”入口及明确空状态。
- 收藏后无需刷新即可在收藏库看到该候选人，取消后立即消失；收藏库不展示上传入口或邮箱来源筛选，避免与完整简历库混淆。
- 现有简历库和候选人详情仅向当前用户返回自己的 `is_favorited` 状态。后续招聘流程中的“加入岗位”必须创建独立的“候选人 × 岗位”应聘记录，不能以收藏代替。

#### 非范围

- 团队共享收藏夹、共享人才池、收藏分组、标签、备注、提醒、@成员、权限转交。
- 批量收藏/取消收藏、基于收藏自动推进流程、自动邀约、自动淘汰、自动录用，以及收藏排行榜或成员行为分析。

## A2. 简历评分

### 用户目标

招聘人员按自己的评价方式配置维度和权重，系统用 AI 分析事实并由后端计算最终分数。

### 功能需求

1. 用户可创建评分模板：名称、说明、维度、每个维度的权重和评分指引。所有维度统一使用 0 至 100 分制，不再配置单项满分。
2. 权重总和必须为 100；允许某个维度为 0。
3. AI 仅对每个维度输出原始分、理由、关联事实和不确定项。
   - AI 生成的评分理由、待确认项、综合判断和风险提示统一使用简体中文；必要的公司名、学校名、职位名和技术名词可保留原文，但不得输出英文完整句或英文段落。
4. 后端按固定公式计算总分，不接受模型自算总分：

       总分 = Σ（维度原始分 / 100 × 维度权重）

5. 结果展示总分、维度分、权重、依据、风险提示、评分模板版本和事实版本。
6. 允许招聘人员手工调整单个维度，但必须填写原因并保留审计记录。
7. 支持按评分模板一键为全部可评分简历创建后台评分任务。任务展示排队、完成、失败和复用历史结果数量；同一模板版本和事实版本已有结果时必须复用，失败项按有限次数自动重试。

### 验收标准

- 修改权重后重新计算的总分符合公式。
- 页面可区分 AI 原始分、人工调整分和最终分。
- 没有证据的维度必须显示信息不足，不得虚构理由。
- 批量评分不得由浏览器并发逐份调用模型；刷新页面后仍可查看任务进度和失败原因。

## A3. AI 简历总结

### 用户目标

快速阅读一份中文、简洁、适合招聘判断的候选人概览。

### 功能需求

1. 对已启用且当前事实快照就绪的简历自动生成中文总结，固定输出：候选人定位、教育背景、工作/实习、核心技能、代表项目/成果、优势、待核实项。上传、文本提取和事实提取的 HTTP 请求不得等待总结模型返回。
2. 总结仅基于已验证的结构化事实，不能使用文件名、联系方式或未经证据支持的推断。
3. 自动总结任务必须按 `resume_id + facts_version` 去重、持久化排队、记录状态和有限重试；Worker 重启、网页刷新或重复入队不得重复生成同一事实版本的总结。
4. 总结失败或模型暂不可用时，不得撤销已验证简历的 `ready` 状态、筛选资格或既有事实；简历库应继续展示处理状态，并在成功后显示总结预览。
5. 支持重新生成并保留历史版本；允许手工编辑生成新版本。事实版本变化后，旧总结自动成为历史，不得覆盖或误作当前事实版本的结论。
6. 简历库仅展示总结预览，不展示完整结构化事实或敏感个人信息。

### 验收标准

- 总结为简体中文，技术名词可保留原文。
- 总结中的每个事实可回溯到简历事实版本。
- 无可用事实时提示“信息不足”，而不是生成空泛结论。
- 新上传并完成事实提取的简历无需人工点击即可完成后台总结；总结队列失败时，该简历仍可正常筛选和查看原件。

## A4. JD 匹配度评分

### 用户目标

按不同岗位比较候选人与 JD 的匹配程度，清楚看到硬条件、缺口和待追问内容。

### 功能需求

1. 用户可创建、保存、切换 JD；JD 包括岗位名称与原始文本。
2. AI 从 JD 中提取可编辑的要求，区分必须条件与优先条件，并关联 JD 原文条款。
3. JD 只有确认后才可用于匹配；确认后的版本不可静默修改，改动必须新建版本。
4. 对单份或全量简历运行 AI 匹配。每份结果包括：
   - 0 至 100 匹配分；
   - 硬条件状态：通过、未满足、信息不足、无硬条件；
   - 每条要求的满足状态、理由、事实依据、缺口或不确定项；
   - 简历事实版本和 JD 版本。
5. 支持该 JD 的排行榜与批量任务进度。
6. 招聘 Agent 可启动批量匹配、展示排行榜，并按明确指令为当前工作区创建全量评分任务；单人匹配解释和评分细则在候选人详情页查看，不由页面当前选择隐式传给 Agent。

### 验收标准

- 硬条件不满足时，即使总分高也必须明确显示。
- 同一候选人在不同 JD 下保留独立匹配结果。
- 批量匹配按后台任务执行，页面可查看总数、完成数和失败数。

# 6. 高级版 B PRD

## B0. 高级版目标

减少简历收集和 JD 编写的重复劳动，把岗位需求沉淀为可复用、可确认的招聘输入。

## B1. 收简历邮箱自动收集

失败附件的精确重试、状态与审计规则见 [邮箱附件失败与单附件重试 PRD](MAILBOX_ATTACHMENT_RETRY_PRD.md)。

一个工作区支持多个可命名收件邮箱的配置、同步、来源追溯、迁移和隔离规则见[工作区多命名收件邮箱 PRD](MULTI_NAMED_MAILBOX_PRD.md)。

### 用户目标

将发往指定招聘邮箱的简历自动进入简历库，无需逐份下载再上传。

### 功能需求

1. 用户配置一个或多个“简历收件地址”，可按岗位、部门或来源命名。
2. 系统通过 IMAP、邮件服务商 API 或入站邮件 Webhook 接收邮件，具体 Provider 可替换。
3. 自动读取邮件元数据：发件时间、收件地址、主题、来源标识、附件名和附件哈希；首期不以发件人姓名或邮箱作为候选人结论。
4. 仅接收 PDF 附件；非 PDF、加密、超大或损坏附件记录失败原因，不进入可筛选库。
5. 合格附件进入与手工上传相同的 PDF 解析和 AI 提取流程。
6. 使用邮件唯一标识、附件哈希和收件地址做幂等，避免轮询、转发、重复投递导致重复入库。
7. 邮件收件箱提供状态：已收取、处理中、已入库、重复、附件不支持、解析失败。
8. 支持暂停某个收件地址、重新处理单封邮件、按保留期清除邮件正文和附件副本。

### 非范围

- 不自动回复候选人。
- 不自动发送拒信或面试邀约。
- 不抓取第三方招聘平台私信。

### 验收标准

- 同一邮件被多次拉取时，简历只入库一次。
- PDF 附件与手工上传得到相同的解析状态和数据质量校验。
- 收件记录可追溯到邮件来源，但简历工作台不展示候选人邮箱。

## B2. AI-JD 撰写

### 用户目标

用户输入岗位需求、业务背景和人才画像后，快速得到可编辑、可发布、可用于匹配的 JD 初稿。

### 输入

- 岗位名称与职级；
- 业务背景、团队职责、产品/项目阶段；
- 必须技能、经验、学历或专业要求；
- 加分项；
- 用人画像、工作地点、薪资或其他公开字段（可选）；
- 写作风格和篇幅（可选）。

### 功能需求

1. AI 生成 JD 初稿，至少含岗位职责、任职要求、加分项、团队/业务介绍和招聘提示字段。
2. 明确区分“用户提供的事实”“AI 建议补充”“待用户确认”。
3. AI 不得生成违法歧视性要求，不得将年龄、性别、婚育、籍贯等作为默认要求。
4. 用户可逐段编辑、重新生成指定段落、保存草稿、创建版本和确认版本。
5. 确认后的 JD 可直接进入基础版 A 的要求提取与简历匹配流程。
6. 每次生成记录输入版本、提示词版本、模型版本和输出版本。

### 验收标准

- 用户提供“业务需求 + 人才画像”后，可生成完整 JD 草稿。
- 用户编辑后仍能保留版本历史。
- 从 AI-JD 确认进入 JD 匹配时，匹配结果引用的是确认版本而非草稿。

# 7. 专业版 C PRD

## C0. 专业版目标

将“简历信息、岗位要求、线上面试、线下面试”串成连续的人才评估辅助流程，为 HRBP 提供可解释的综合参考。

## C1. 线上面试题撰写

### 用户目标

快速生成适合远程视频、电话或笔试前沟通的标准化题目与评分锚点。

### 功能需求

1. 输入来源：确认的 JD、候选人匹配缺口、职位级别、面试时长、面试类型。
2. 输出题目按维度分组：岗位专业能力、项目经历核验、问题解决、协作沟通、动机与稳定性、风险核验。
3. 每题包含：提问目的、主问题、追问、理想信号、风险信号、建议评分锚点、关联 JD 要求。
4. 支持选择题目、排序、编辑、生成线上面试提纲和记录表。
5. 面试官记录回答时，可标记“有证据”“待核实”“不确定”；AI 不得把未记录的表现写为事实。

### 验收标准

- 至少 70% 的题目能关联一条 JD 要求或候选人待核实项。
- 线上题可导出为面试官使用的提纲。

## C2. 线下面试题撰写

### 用户目标

生成更适合现场深挖、白板讨论、情景演练和跨面试官协同的题目。

### 功能需求

1. 基于 JD、候选人简历、线上面试记录和岗位级别生成题库。
2. 除 C1 的题目字段外，支持：现场案例、角色扮演、白板/作品讨论、观察点、时间建议、面试官分工。
3. 允许不同面试轮次使用不同重点，例如技术深挖、业务协同、管理能力、文化匹配。
4. 每题需提示适用边界，避免把非岗位相关的个人偏好写成评价标准。
5. 可生成线下面试评分表，维度与评分锚点可由 HR 编辑。

### 验收标准

- 题目能区分线上已核实项与线下待深挖项。
- 每轮面试至少给出目标、时长、题目、追问和评分维度。

## C3. HRBP AI 面试结果参考

### 用户目标

将结构化面试记录与简历、JD 匹配结合，生成供 HRBP 阅读的“建议参考”，而不是替代最终的人事决定。

### 输入要求

- 已确认 JD 与版本；
- 候选人简历事实与版本；
- 线上/线下面试题目及实际回答记录；
- 每位面试官的结构化评价、分数、证据和待核实项；
- 可选的 HRBP 关注点。

### 输出要求

1. 生成综合参考，固定包含：
   - 岗位匹配概览；
   - 已验证优势；
   - 风险与分歧；
   - 线上与线下结论是否一致；
   - 尚待核实的问题；
   - 建议选项：建议推进 / 建议补充面试 / 建议谨慎评估；
   - 建议理由和关联证据。
2. 输出必须区分“候选人明确回答”“面试官评价”“AI 推断的待确认事项”。
3. 存在面试官分歧时，必须展示分歧，不得将多数意见伪装为事实。
4. 不输出自动录用、自动淘汰或不受人工复核的最终结论。
5. HRBP 可添加最终人工决定与原因，人工决定不被 AI 覆盖。

### 验收标准

- 没有面试记录时，系统不得生成“面试通过/不通过”结论。
- 每条综合结论可回溯到简历事实、JD 条款、题目回答或面试官记录。
- 输出中明确显示“AI 面试结果参考，不替代人工决定”。

# 8. 招聘 Agent

招聘 Agent 是全版本共用的独立对话工作台页面（`#agent`），不是独立的决策系统。它保留产品的全局主导航，不使用右侧聊天抽屉，也不额外创建会话历史侧边栏。

| 能力 | 基础版 | 高级版 | 专业版 |
| --- | --- | --- | --- |
| 自然语言筛选、排行榜、匹配解释 | 是 | 是 | 是 |
| 直接生成/修订人才画像草案、确认后找人 | 是 | 是 | 是 |
| 创建/选择 JD、启动批量匹配 | 是 | 是 | 是 |
| 查询收件邮箱状态、生成 JD 草稿 | 否 | 是 | 是 |
| 生成面试题、整理面试记录、输出 HRBP 参考 | 否 | 否 | 是 |

Agent 只可调用显式注册的后端工具。它可以主动执行筛选、批量匹配和当前工作区全量评分任务，但不能删除数据、修改原始简历事实、自动发信、自动拒绝候选人、隐式读取页面当前候选人，或代表 HR 作出最终决定。人才画像草案阶段禁止候选人读取、搜索、评分和 JD 匹配；只有 HR 确认并明确启动后才进入找人运行。

每轮回复可以展开“本轮处理过程”，仅显示服务端产出的安全工具摘要和完成状态，帮助 HR 理解结论来自哪些受控操作。该安全摘要随短期会话恢复，但不进入模型上下文；只保留有长度边界的工具显示名和面向 HR 的结果概述。该展示不得等同或替代模型思维链：不暴露隐藏 Prompt、内部推理、原始工具 JSON 或参数、候选人 ID、简历全文或 Provider 载荷。

# 9. 通用非功能需求

## 9.1 权限与隐私

- 系统采用注册用户、工作区成员与平台管理员三层身份；所有简历、原文件、筛选、评分、JD、Agent 和邮箱接口必须受会话与当前工作区双重保护。
- API Key、收件邮箱密钥和邮件 Provider 凭据只能保存在服务端环境变量或密钥管理系统。
- 原 PDF 只能通过已登录会话访问；下载、查看、删除和导出应记录审计日志。
- 发送给模型的数据遵循最小必要原则，默认脱敏电话、邮箱、地址等非必要个人信息。

## 9.2 性能与可靠性

- 文件解析、AI 提取、批量匹配、收件轮询、JD 生成和面试材料生成应支持异步任务、重试和状态查询。
- 批量任务须展示排队、运行、成功、失败数量和失败原因。
- 所有写入接口应具备幂等或重复提交保护。
- 生产环境使用 HTTPS、PostgreSQL、备份与运行监控；在 HTTP 临时环境中不得迁移真实简历数据。

## 9.3 可解释性

- 筛选展示命中字段。
- 通用评分展示维度、权重、事实依据和不确定项。
- JD 匹配展示要求、证据、缺口和硬条件状态。
- 面试参考展示来源类型和未确认信息。

## 9.4 平台管理员控制台（内部能力）

平台管理员控制台是 GreatSell 内部运营控制面，不属于基础版、高级版或专业版的客户功能，也不受某个工作区套餐开关控制。详细设计见 [平台管理员控制台设计](PLATFORM_ADMIN_CONSOLE_DESIGN.md)。

- 仅 `is_platform_admin=true` 的有效账号可进入 `/platform`；工作区 `admin` 与 `recruiter` 均无权访问平台 API。
- 信息架构包括总览、工作区、用户、套餐、AI 管理和审计日志。
- 跨工作区视图只展示工作区、账号、套餐、试用、AI 用量与成本等运营元数据，不展示候选人、简历、原文件、JD、评分、邮箱内容、Prompt 或模型输出。
- 允许受控调整工作区名称、套餐、状态、试用截止时间和普通用户启用状态；禁止停用当前操作者或其他平台管理员。
- 套餐、工作区、用户和 AI 配置变更必须记录操作者、目标、原因、请求 ID 与脱敏的前后差异；历史版本、成本账本和审计记录不得硬删除。
- 不提供用户冒充、租户会话接管、候选人内容查看、真实密钥管理、服务器运维或招聘自动决策能力。
- 收费接入后，套餐目录、价格版本、订阅生命周期、支付事件和功能授权应保持分层；当前控制台不伪造支付、退款、开票或账单操作。

### 验收标准

- 匿名请求平台 API 返回 `401`，普通工作区成员返回 `403 platform_admin_required`。
- 平台管理员身份不会绕过现有工作区业务 API 和原文件的租户隔离。
- 关键写操作均有不可变审计，响应和日志不含密钥、候选人内容或模型原文。
- 1440px、1024px、768px 和 375px 视口下核心查看与受控操作可达，移动端使用侧栏抽屉而非底部导航。

## 9.5 自助注册试用与大模型调用额度

- 每个完成注册并验证邮箱的新工作区获得 30 天进阶版试用，以及累计 1,000 次大模型调用额度。
- 额度按工作区快照管理，和 DeepSeek 或任何其他 Provider、模型、路由、功能开关无关；切换模型、重试、备用模型和 Agent 多轮调用不能绕过它。
- 计数单位是一次真实的外部大模型调用。简历提取、评分、总结、JD 生成与要求提取、JD 匹配、姓名补全和招聘助手均统一计入；未出站的路由/凭据/请求校验失败不计入。
- 服务端必须在外部调用前以原子方式预扣一次额度，并与调用账本一起提交。达到 1,000 次后不再向 Provider 发起第 1,001 次请求。
- 额度耗尽或试用到期后，已有候选人和原件继续保留，用户仍可访问非 AI 数据管理功能；系统只拒绝新的大模型调用，并明确显示已用、上限、剩余次数和可理解的原因。
- AI Worker、批量任务和 Agent 必须与同步 HTTP 请求使用同一个网关约束，不能因后台执行或跨工作区任务而漏计或越权。

### 验收标准

- 注册页与已登录工作台均以服务端数据展示试用天数和 1,000 次额度，不在浏览器侧维护可篡改的计数。
- 同一工作区的第 1,000 次外部大模型调用成功，第 1,001 次在网络请求前拒绝；重试、fallback 与 Agent 多轮均被验证为逐次计数。
- A 工作区额度耗尽不影响 B 工作区；非试用的 active 工作区不受该试用上限影响。
- 额度耗尽、试用到期和工作区停用的后台任务均以稳定错误结束且不无意义重试。

## 9.6 使用体验反馈与调用额度赠送

- 已验证的工作区成员可从右上角账户菜单进入“提交宝贵意见”。入口明确说明：系统审核通过后赠送当前工作区 500 次 AI 调用额度，不承诺具体发放时长。
- 反馈采用开放式体验问卷，不做星级、NPS 或主观评分。四项文本题和联系电话必须全部填写：本次使用场景、希望完成的目标、最不顺的地方、希望如何改进、联系电话。
- 用户可选附加 PNG、JPG/JPEG 或 WebP 截图、手写说明照片；原文件必须保存在私有工作区命名空间，不能作为公开静态资源或暴露存储路径、哈希。
- 奖励属于工作区共享额度，不属于填写者个人。成功提交后进入服务端系统审核处理队列；系统审核通过后由后台 Worker 增加 500 次，具体时长不向用户承诺。
- 每个工作区每 8 小时只能成功提交一次有奖励的问卷。冷却由服务端以原子写入控制；同一工作区多个成员、多个浏览器标签或 API 副本不能并发获得多份奖励。
- 提交必须支持幂等重试。相同重试标识和相同问卷只能生成一条奖励记录；因网络重试而新写入但未被引用的截图必须清理。
- 工作区成员只能查看自己提交的问卷和附件；平台管理员可在只读“用户反馈”页面查看工作区、提交人、联系电话、四项原文、受保护附件及奖励状态，但没有审批、拒绝或手工发放控件。
- 用户侧状态仅显示“系统审核中，审核通过后发放 500 次 AI 调用额度”“系统审核通过，正在发放当前工作区额度”或“已到账，当前工作区已增加 500 次 AI 调用”。

### 验收标准

- 四项未填全、联系电话缺失或非法、非法图片、超出图片数量或图片大小限制均不能创建反馈或占用奖励冷却。
- 到期前 Worker 不发放额度；到期后并发或重试执行也只能将同一工作区额度增加一次 500。
- A 工作区、其他成员和匿名请求均不能读取 B 工作区用户的反馈正文或截图；平台管理员仅通过独立平台权限访问反馈。
- 用户提交后不刷新页面也能看到“处理中”；刷新、重新打开页面或额度到账后均能得到服务端真实状态。

## 9.7 历史工作区一次性接管与旧口令退役（后续增强）

### 目标

允许历史单账号/管理口令工作区在不复制候选人、简历、JD、评分、邮箱配置或 AI 数据的前提下，由经过邮箱验证的新企业管理员一次性接管，并彻底切换到正式账号体系。

### 核心规则

1. 仅已登录、邮箱已验证、且为当前工作区唯一有效管理员的账号可发起；必须提交历史管理口令作为一次性证明。该口令仅用于当次校验，绝不保存、记录或在响应中返回。
2. 发起账号所属的新工作区必须为空，且没有其他有效成员或待处理邀请；源历史工作区也不得有其他有效成员或待处理邀请。任一条件不满足即返回冲突，且零业务数据变更，不得基于猜测驱逐成员。
3. 接管在单个事务中完成：新账号成为历史工作区管理员；原空工作区被挂起而非删除；历史占位账号/成员被禁用，所有历史会话失效；未使用的 OAuth 意图、临时原件/导出授权被撤销；仅将历史占位账号的 Agent 会话转给新账号，不转移其他真实用户的私有会话。
4. 接管保留历史工作区 ID、全部业务记录和原始存储路径，不复制表数据，不批量改写 `organization_id`。接管后新增上传仍写入原历史工作区命名空间。
5. 操作必须一次性且幂等：并发尝试或重试最多一个成功，不得产生重复成员、重复数据或重复会话转移；接管成功后旧口令不得再用于登录、API Header 鉴权或任何回退入口。
6. 任何无明确工作区上下文的内部查询必须落入空的系统工作区，绝不能默认回退到历史工作区。

### 验收标准

- 接管后的管理员可访问原有简历、原件、JD、邮箱配置及历史占位账号的 Agent 会话；跨工作区资源 ID 仍统一返回 `404`。
- 旧 cookie、旧口令和旧 Header 鉴权在接管后全部不可用；旧占位账号重启或重试后不得恢复访问。
- 目标工作区非空、源工作区存在成员/邀请、并发接管或重复请求均不得复制或丢失数据；不安全条件必须返回 `409` 且零变更。
- 必须覆盖迁移、跨工作区越权、会话失效、原件访问和重试幂等测试，并完成注册、邮箱验证、登出/重新登录的浏览器回归。

### 非范围

- 删除历史候选人、文件或业务记录；合并两个非空工作区；平台管理员自动接管；旧口令找回；平台管理员查看候选人内容；任何生产环境、域名、DNS 或密钥变更。

# 10. 明确不做

- 自动拒绝、自动录用、自动发送 Offer、自动发送候选人消息。
- 基于敏感属性做筛选、排序或判断。
- 未经用户授权地抓取第三方招聘平台或候选人社交账号。
- 不允许跨工作区共享、检索或导出候选人数据，也不提供平台管理员冒充租户成员的能力。
- 将模型输出视为无需人工审阅的事实或最终招聘决定。

# 11. 发布顺序与完成定义

1. **基础版 A：** 四项招聘核心能力稳定可用，Agent 可调用筛选、批量匹配、排行榜和工作区全量评分工具；单人评分细则与匹配解释在候选人详情页可追溯查看。
2. **高级版 B：** 邮箱收件流程通过幂等、异常处理与数据保留验证；AI-JD 草稿到确认 JD 的流程完整。
3. **专业版 C：** 面试题、结构化记录、线下/线上整合与 HRBP 参考均可追溯，且不产生自动人事决定。

每个版本上线前必须通过功能验收、权限校验、数据脱敏检查、异常任务重试检查和真实招聘样本评估。
