## 2. 目标

登录页统一使用最新产品名「大卖智聘」，完整定位为「大卖智聘｜AI 招聘决策工作台」；
现有「大卖数智」Logo 继续作为母品牌标识。

本次只调整客户可见文案和页面标题，不改变布局、表单、登录接口、邮箱验证或其他认证逻辑。

## 5. 实施方式

1. 实施前重新 fetch；从当时最新的 `origin/main` 创建独立
   `agent/auth-product-naming` worktree，不使用当前落后的本地主工作区。
2. 若 PR #148 或 #154 已合并，先读取合并后的最终组件，再在其基础上应用本计划；
   不把这些 PR 的业务改动复制进命名分支。
3. 修改认证页文案、浏览器标题映射和产品命名规范；仅在实际发生换行或溢出时做最小
   CSS 调整，不重新设计页面。
4. 在 375px、768px、1440px 检查产品名不溢出，表单、按钮、焦点顺序和认证操作保持正常。
5. 检查认证入口不再出现客户可见的旧产品名称，同时确认 Logo 和品牌替代文本仍为
   「大卖数智」。
6. 运行完整后端测试、前端生产构建、关键登录 Playwright 路径和 `git diff --check`。
7. 创建独立 PR 并提供本地预览。获得确认后再 squash merge，不直接修改服务器业务代码。

## 6. 并行开发与兼容性

- 当前 PR #148 会移除旧版静态认证，并修改同一登录组件。
- 当前 PR #154 会修改认证页面所在的 `App.tsx`，但不会替代本计划中的产品文案。
- 本任务不夹带 PR #148 的认证逻辑、迁移或配置，也不夹带 PR #154 的工作台功能。
- 若 PR #148 先合并，本任务必须基于合并后的最新 `origin/main` 重新应用文案并复测。
- 若本任务先合并，PR #148 更新基线时必须保留本计划定义的新产品文案。
- 任一相关 PR 合并后，后续 PR 必须更新到新的 `origin/main` 并重新跑完 CI，不能沿用旧绿灯。

## 7. 发布与上线验证

1. PR 合并后，等待 `main` 来源证明、生产镜像构建和运行时回归通过。
2. 等待 **Staging release** 自动创建不可变 `stg-*` 标签、部署隔离 staging 并完成公网
   smoke。
3. 在 staging 检查登录、注册、找回密码、设置新密码、验证邮箱和工作台标题。
4. staging 确认通过后，由负责人从 `main` 手动运行 **Production promotion** 并输入
   `PROMOTE`。
5. 生产晋级完成后验证 HTTPS 首页、`/login`、`/register`、`/forgot-password`、
   `/reset-password`、`/verify-email` 和 `/health`，并检查公开页面标题。

## 8. 验收标准

- 登录页清晰显示「大卖智聘｜AI 招聘决策工作台」和「登录大卖智聘」。
- 「大卖数智」Logo、品牌首页链接和替代文本保持不变。
- 登录、注册、找回密码、设置新密码、验证邮箱及工作台标题与本计划一致。
- 登录、注册、找回密码、邮箱验证和原有工作台访问流程无行为变化。
- 没有新增 API、数据迁移、套餐、价格、试用权益或邮件配置变更。
- staging 与生产使用同一份已经通过 CI 的镜像；生产页面与 staging 确认文案一致。
