# 简历筛选 V3 — 产品需求文档（PRD）

**版本：** V1.0  
**日期：** 2026-07-16  
**产品代号：** Resume Screening V3  
**本文状态：** 评审稿

## 1. 背景与问题

现有系统长期以 resume_text 为中心：简历来源混杂、文本质量不稳定、同一候选人可能有多个版本，且结构化结果缺乏可追溯证据。因此，按学历、技能、工作年限等条件筛选时，无法稳定判断结果是否可信。

V3 是一个独立重写项目，不迁移旧 resume_text 作为可检索事实，也不修改旧系统的数据。所有进入 V3 的简历必须由用户重新上传，并通过新的解析、校验和结构化流程。

已验证的技术事实是：不能只依赖未经校验的文档解析结果。V3 必须先读取原生 PDF 文字层，校验页数和文字覆盖率；不合格时进入异常处理（重试或重新上传）。大模型只能处理已提取且有证据的内容，不能补回解析阶段遗漏的页面。

## 2. 产品目标

第一阶段交付三个招聘基础能力：

1. 简历按条件筛选。
2. 用户配置评分权重，系统基于简历事实和 AI 分析给出评分。
3. AI 分析简历与岗位 JD 的匹配度。

产品需要让招聘人员能回答三个问题：

1. 这个候选人为什么被筛出来？
2. 这个分数由哪些事实和权重构成？
3. 系统不确定时，是否明确标记异常或排除无证据字段，而不是假装准确？

## 3. 成功标准

### 3.1 产品结果

- 招聘人员可在一个筛选页中组合学历、985/211、专业、技能、工作年限、公司/岗位等条件。
- 每条筛选结果可显示命中的字段和来源证据，不需要阅读整份简历才能理解命中原因。
- 所有已上传 PDF 都必须出现在可分页的简历库中；招聘人员能直接看到最新 AI 评分和处理状态。
- 用户修改评分权重后，可以重新计算候选人分数，并看到各维度分数。
- 每个候选人与指定 JD 都可获得匹配分、匹配项、缺口和风险说明。

### 3.2 质量门槛

- 解析成功的 PDF，源页数与已解析页数必须一致；不一致不能自动进入可筛选状态。
- 所有可检索的教育、经历、技能字段必须能回溯到原文证据块。
- 项目、竞赛、课程设计、科研、社团、获奖不得自动计入正式工作年限。
- AI 可依据随请求提供、版本化的 985/211 规则文档产生二值初判和 roster ID；服务端必须用同一版本本地表复验。未命中或不确定均为 false；通过字段级原文证据校验的 AI 结果自动进入筛选。
- 无证据或不确定的字段不得伪装成 false、0 年经验或“无技能”：无证据字段被剔除并记录质量标记；无法得到可用结果的简历进入异常处理。

## 4. 用户与账号

首期只提供一个账号。该账号同时承担招聘、配置和系统管理职责：

- 上传简历、创建岗位 JD、配置评分权重。
- 查看筛选命中、评分和 JD 匹配。
- 查看原始简历、AI 评分与异常原因，并可重新上传或重试失败任务；招聘工作台不展示原始结构化事实明细。
- 管理院校别名、模型配置和数据保留设置。

首期不做成员管理、角色权限、团队共享、多组织隔离、候选人端、外部 ATS 同步或自动外呼。

## 5. 核心业务流程

    新上传原始简历
        → 文件安全校验与版本存储
        → 原生文本提取
        → 页数/文字质量校验
        → 布局/证据块整理
        → 持久化 AI 事实提取任务（queued / running）
        → 严格 Schema 的 AI 事实提取
        → 本地归一化与规则校验
        → 字段级原文证据校验
        → ready（自动激活并进入筛选） / needs_review（异常待处理） / failed
        → 条件筛选、评分、JD 匹配

新版本只有在状态为 ready 时才能替换候选人的当前可检索简历。新版本异常、失败或尚未完成时，保留候选人此前已通过的版本；首期不设置人工确认关卡。

## 6. 范围与非范围

### 6.1 本期范围

- 仅支持 PDF 简历重新上传、版本管理、原文件保存。
- 原生 PDF 文本提取、质量检测、自动入库与异常状态。
- 教育、经历、技能等事实的结构化、证据留存和归一化。
- 985/211 单一布尔属性。
- 条件筛选与命中解释。
- 评分模板、可配置权重、简历评分。
- JD 创建、JD 解析、JD 匹配分析。
- 单账号访问控制、审计、测试和数据导出删除能力。

### 6.2 明确不在本期范围

- 迁移旧系统 resume_text 并把它当成 V3 事实来源。
- DOCX、图片等非 PDF 简历格式。
- OCR 接入和任何 OCR Provider 依赖；待真实新上传样本评估后再决定是否建设。
- BOSS、猎聘、拉勾等平台自动抓取与自动投递。
- 面试排期、Offer、入职、薪酬审批。
- 对候选人做性别、年龄、地域、照片、婚育等敏感属性的自动淘汰或排序。
- 自动拒绝候选人；系统只辅助决策，最终决定由招聘人员作出。

## 7. 功能需求

## 7.1 模块 A：简历上传、解析与自动入库

### A1. 上传

- 首期仅接受 PDF；文件扩展名、MIME 类型和 PDF 文件头都必须通过校验。
- 每次上传创建一个新的简历版本，不覆盖原始文件或旧版本。
- 文件入库时计算 SHA-256，用于识别重复上传，但重复文件仍可关联到不同候选人。
- 原始文件、提取文本、解析块、结构化事实和模型结果均记录版本号与创建时间。
- 上传者可填写候选人显示名，也可先上传后关联候选人。
- 原生文字质量合格时，上传事务内必须创建持久化 AI 提取任务；上传请求不得等待模型调用，刷新或关闭浏览器不得丢失任务。
- AI 任务在字段级原文证据校验和本地规则校验通过后，自动将简历设为 `ready`、激活并放入筛选索引；上传请求本身始终异步返回，不等待模型。

### A2. 文本提取与质量校验

- 默认路径：原生 PDF 文本提取优先。
- 记录源 PDF 页数、每页字符数、可提取文字页数、乱码比例和解析器版本。
- 以下任一情况直接进入 `needs_review` 异常状态：

  - 源页数和解析页数不一致；
  - 存在内容页但提取文字接近为空；
  - 文字量显著异常；
  - PDF 加密、损坏或无法读取；
  - 解析后的关键字段无法被证据块支撑。

- 首期不调用 OCR。扫描件、图片型 PDF 或文字质量不合格的文件，标记具体原因并提示重新上传；必要时可重试 AI 任务。
- PaddleOCR、MinerU、Docling 等工具均属于后续可评估的扩展，不得绕过质量门槛。

### A3. 解析状态

    uploaded → 原生文字解析 → text_ready → AI queued / running → AI completed → ready（自动激活）
                              ↘ needs_review（无可用文字、扫描件、解析质量异常或 AI 无可用结果）
                              ↘ failed

AI 任务状态独立于 PDF 解析状态：`queued`、`running`、`completed`、`needs_attention`、`unavailable`。`completed` 表示通过证据校验的事实已落库，简历同时为 `ready` 且激活。

只有 ready 进入搜索索引。`needs_review` 是内部异常待处理状态，不是人工确认队列；界面必须展示原因，例如 `parsed_page_count_mismatch`、`ai_extraction_*`、`work_context_ambiguous`，并提供重试或重新上传。

### A4. 异常处理与审计

- 没有人工确认、手工修正或“确认后入库”步骤。AI 成功后自动启用。
- 当前唯一账号可查看原始简历、提取块和结构化字段的对应关系，以及所有质量标记和任务错误。
- 无可用原生文字、AI 失败或无可用字段时，只提供重新上传和 AI 重试；异常版本不得替换当前可筛选版本。
- 自动入库、重试、重新上传和删除均记录时间、原因、旧/新版本，供审计追溯。

### A5. 简历库（上传汇总）

- 简历库是桌面端默认入口；每一份成功保存的 PDF 无论 AI 尚在排队、已启用或异常，都必须有一行记录。
- 列表只展示候选人/文件名、最新 AI 评分、处理状态、上传时间和打开入口；不展示教育、经历、技能等结构化事实字段。
- AI 评分尚未运行时明确显示“尚未评分”，不得用空值或默认分数伪装为结果。
- 打开一行后提供“原始文件”“评分详情”和“提取依据”内容页；评分从简历库的“去评分”进入评分规则页面。
- 提取中状态自动刷新；异常状态显示为需要处理，原始 PDF 仍可打开。

## 7.2 模块 B：结构化简历事实

### B1. 最小字段

| 类别 | 字段 |
| --- | --- |
| 简历版本 | 文件哈希、原文件名、页数、解析状态、质量标记、解析器版本 |
| 教育经历 | 学校原文、归一化学校、专业原文、学历、起止日期、证据块 |
| 经历 | 类型、经历/项目/竞赛名称原文、机构/主办方原文、担任角色/岗位原文、起止日期、是否在职、经历证据块、逐条职责/工作内容/贡献及各自证据块 |
| 技能 | 展示名称、标准键、证据块 |
| 聚合事实 | is_985_211、最高学历、正式工作月数、正式工作加实习月数 |

### B2. 经历类型

经历必须分为：

- employment：正式工作。
- internship：实习。
- project：项目。
- competition：竞赛。
- other：其他。
- unknown：无法确定。

只有 employment 和 internship 能在相应筛选条件中计入工作年限。默认的“工作年限”只计算 employment；“含实习年限”是一个单独条件。

模型若没有明确的组织和任职/实习关系，不得输出 employment 或 internship。项目标题中的“负责人”“数据分析师”等角色，不能因为包含岗位词就被计为工作。

每一段工作、实习、项目、竞赛或其他明确活动都应保留为一条经历：

- `experience_name_raw`：经历、项目、比赛或活动的明确名称；原文未写则为空。
- `title_raw`：候选人在该经历中担任的职位或角色；原文未写则为空。
- `detail_items`：逐条保存原文明确写出的职责、实现、贡献、成果和产出。每一条都单独关联其原文证据块，不得把多条事项合并为概括性总结，也不得补写简历中没有的内容。

这套明细既适用于正式工作和实习，也适用于项目、比赛、课程设计、科研和其他活动；只有经历类型会影响工作月数，职责明细本身不参与年限计算。

### B3. 985/211

需求只保留一个字段：

    is_985_211: true | false

规则：

- 任意教育经历匹配本地院校表中 is_985_211=true 的学校，结果为 true。
- 明确匹配到非 985/211 学校，且没有任何命中学校，结果为 false。
- AI 学校名无法可靠归一化、未命中名单或无法确认时，AI 初判字段为 false；只要该学校原文和其他保留事实均通过证据校验，简历自动进入筛选。

本地院校表必须支持全称、常见简称、历史名称和校区别名，并可由管理员更新。院校表每次变更需要有版本和来源记录。

### B4. 证据与可信度

- 每个模型抽取字段至少关联一个 source_block_id；经历中的每条 `detail_items` 也必须有自己的证据块。
- 每个 source block 记录页码、块类型、文本、位置坐标（可用时）和解析器版本。
- 后端校验字段值是否存在于其证据文本；失败的单个字段或职责条目会被剔除并留下质量标记，不能凭空进入筛选事实。
- source_grounded 仅代表“值可在原文找到”，不等于“语义已完全正确”。经历类型语义不确定时存为 `unknown`，不计入对应工作年限或经历筛选条件；不会为此阻塞整份已校验简历自动入库。

## 7.3 模块 C：条件筛选

### C1. 可筛字段

首期支持：

- 是否 985/211。
- 最高学历。
- 学校名称。
- 专业关键词。
- 正式工作月数、含实习工作月数。
- 经历类型。
- 公司/机构名称。
- 职位名称。
- 技能：全部具备、任一具备。
- 简历关键词（仅作为辅助条件，并标记命中位置）。

### C2. 筛选语义

- 顶层条件之间使用 AND。
- 学历条件组之间可选 OR。
- 同一条教育经历内的学校、专业、学历条件使用 AND，避免跨教育经历拼接误命中。
- 同一条经历内的机构、职位、类型、日期条件使用 AND。
- 技能 all_of 必须全部满足；any_of 至少满足一项。
- 默认只搜索当前激活且状态为 ready 的简历。
- unknown 不自动满足也不自动否定任何条件；界面显示“未纳入对应条件”的提示，不设置待人工确认队列。

### C3. 结果页

每个候选人展示：

- 候选人显示名和当前简历状态。
- 985/211、最高学历、工作月数、关键技能。
- 命中理由，例如“985/211：是；技能：Python、SQL；正式工作：24 个月”。
- 查看 AI 评分和原始 PDF 的入口。

结果页默认不展示整份简历全文、联系方式或敏感个人信息。

### C4. 筛选保存

- 用户可保存筛选器，命名并复用。
- 保存时记录条件 JSON、创建人和更新时间。
- 后续可扩展为职位绑定筛选器，但首期不强制。

## 7.4 模块 D：简历评分

### D1. 评分模板

招聘人员创建评分模板，每个维度设置权重、满分和说明。首期维度建议：

- 技能匹配。
- 相关工作/实习经历。
- 学历与专业。
- 项目/成果相关性。
- 职位关键词与其他要求。

权重总和必须为 100；每个维度可设置为 0。模板可绑定岗位，也可作为通用模板使用。

### D2. 评分计算

评分由两层组成：

1. AI 根据已验证的结构化事实和岗位要求，输出每个维度的原始分、理由、证据和不确定项。
2. 后端按用户配置的权重计算总分，不能让模型自行决定最终加权公式。

总分计算：

    总分 = Σ（维度得分 / 维度满分 × 维度权重）

输出必须包括：

- 总分、模板版本、计算时间。
- 每个维度得分、权重、理由和证据。
- 缺失信息和风险提示。
- 需要关注的风险或信息缺口。

评分不可作为自动淘汰依据；用户可手动调整并记录调整原因。

## 7.5 模块 E：AI 简历总结

### E1. 输出内容

每份 ready 简历可生成一份结构化总结：

- 候选人定位（一句话）。
- 学历背景。
- 正式工作与实习概况。
- 核心技能。
- 代表项目/成果。
- 优势。
- 待核实项或信息缺口。

### E2. 约束

- 总结只基于结构化事实和证据块。
- 不编造雇主、年限、学校、技术栈或成果。
- 不输出年龄、性别、照片、联系方式等非必要信息。
- 支持重新生成和招聘人员手工编辑；每次生成保留模型、提示词和输入事实版本。

## 7.6 模块 F：JD 匹配度评分

### F1. JD 管理

用户可创建和保存岗位 JD，字段至少包括：

- 岗位名称。
- 岗位描述原文。
- 必须条件。
- 加分条件。
- 经验年限要求。
- 学历/专业要求。
- 必备技能。

JD 原文可由 AI 提取为结构化要求，但用户必须能够编辑和确认。

### F2. 匹配分析

匹配结果包括：

- 总匹配分，0 至 100。
- 必须条件通过情况。
- 加分项命中情况。
- 技能匹配与缺口。
- 经历匹配与缺口。
- 学历/专业匹配。
- 需要面试追问的事项。
- 每项结论对应的简历证据和 JD 条款。

必须条件不满足时，总分仍可生成，但必须显著标记“关键不满足”，不能通过高分掩盖。

### F3. 与通用评分的关系

- 通用评分用于用户自定义的评价模板。
- JD 匹配用于特定职位的职位要求。
- 两者可以同时存在，但必须显示各自的模板/JD 版本，不能混为一个无来源的总分。

## 8. 数据模型与数据生命周期

### 8.1 核心实体

| 实体 | 关键用途 |
| --- | --- |
| candidates | 候选人主体，不直接存解析后的全文事实 |
| resumes | 每次上传的一份原始简历版本 |
| resume_source_blocks | 原文块、页码、坐标和解析证据 |
| resume_educations | 教育经历 |
| resume_experiences | 正式工作、实习、项目、竞赛等经历 |
| resume_skills | 技能 |
| resume_filter_facts | 为筛选优化的聚合事实 |
| institutions / institution_aliases | 本地院校与别名表 |
| score_templates / resume_scores | 评分模板与计算结果 |
| jobs / job_requirements / job_matches | JD、结构化要求和匹配结果 |
| review_actions / audit_logs | 自动入库、异常处理和审计记录 |

### 8.2 版本规则

- 一个候选人可有多份简历。
- 同一时刻最多一份 active 且 ready 的简历参与默认筛选。
- 新版本通过后才替换 active 版本。
- 评分、总结、JD 匹配都引用具体 resume_id、事实版本、模板/JD 版本。
- 删除候选人时，按数据保留策略删除原文件、解析文本、模型输入输出和索引。

## 9. 技术与安全要求

### 9.1 推荐架构

- 前端：React + TypeScript。
- 后端：FastAPI。
- 部署目标：云服务器，使用 Docker Compose 部署前端、后端、异步 Worker 与反向代理；HTTPS、数据库备份和运行监控是上线前置条件。
- 生产数据库：云服务器上的 PostgreSQL；本地开发可用 SQLite。
- 文件存储：开发环境使用本地目录；生产使用云对象存储或 S3 兼容对象存储。
- 异步任务：简历解析、模型调用、批量重算必须异步执行。
- 模型接入：通过可替换 Provider 接口接入 DeepSeek；生产密钥仅来自服务端环境变量或密钥管理服务。
- OCR：首期不接入任何 OCR 服务。保留质量原因和 Provider 抽象的扩展位置，待收集真实新上传样本后再决定是否采用 PaddleOCR 或云 API。

### 9.2 个人信息与模型调用

- API Key 不得写入源码、日志、测试快照或前端。
- 向模型发送最小必要文本；不发送照片、电话、邮箱、住址等非必要内容。
- 模型请求/响应日志默认只保存请求 ID、版本、耗时、状态和脱敏摘要。
- 原文件访问必须经过权限校验；下载和查看行为写入审计日志。
- 支持候选人数据导出、删除和保留期限配置。

### 9.3 可观测性

每个解析任务需要记录：

- 任务 ID、文件哈希、解析器、模型、版本、耗时、状态。
- 源页数、解析页数、文本字数、质量标记。
- 字段抽取数、证据校验成功率、被剔除字段数和异常原因。
- 模型调用 token、成本、失败率和重试次数。

## 10. 验收标准

### 10.1 上传与解析

- 上传一份文字层正常的两页 PDF，系统保存原文件并识别两页；若只解析出一页，状态必须不是 ready。
- 上传扫描件或文字提取不合格的 PDF 时，系统进入 needs_review，不产生虚假的空简历。
- 重传同一候选人简历后，旧版本仍可查看；新版本未 ready 前不影响旧版本筛选。

### 10.2 结构化字段

- 教育、经历、技能每项都可定位到原始证据块。
- 项目/竞赛中出现“负责人”“分析师”等角色时，不得计入正式工作月数。
- 任一教育学校匹配本地 985/211 表时，is_985_211=true。
- AI 学校未能归一化时按二值规则得到 false；原文证据校验通过后仍自动进入筛选。

### 10.3 条件筛选

- 可正确组合 985/211、学历、专业、工作年限、公司/职位、技能筛选。
- 同一条教育/经历内的组合条件不发生跨记录误命中。
- 结果可解释每个条件的命中事实。
- needs_review、failed、非激活版本默认不出现在结果中。

### 10.4 AI 能力

- 改变评分权重后，总分按公式重新计算，并显示各维度证据。
- 总结没有原文未出现的关键事实。
- JD 匹配明确显示必须条件缺口和证据。

## 11. 已确认的首期产品决策

1. 输入格式仅限 PDF。
2. AI 成功提取并通过原文证据校验后自动启用；首期不设置人工确认流程。
3. 首期只支持一个账号，不做成员、团队或模板/JD 共享。
4. 部署目标是云服务器。
5. 首期不依赖 OCR；解析不合格的 PDF 标记异常并要求重新上传，待真实样本评估后再决定 OCR 路线。
