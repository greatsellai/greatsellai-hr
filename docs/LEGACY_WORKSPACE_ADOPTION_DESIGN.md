# 历史工作区接管与旧登录退役设计

**状态：** 待实现
**范围：** 将历史单账号工作区安全接管给一个已注册、已验证的正式账号，并移除浏览器中的旧管理口令登录入口。

## 1. 目标

历史候选人、简历原件、JD、评分、邮箱配置、AI 任务和 Agent 上下文已经归属到固定的历史工作区。此功能让一个正式账号接管该工作区，之后只通过邮箱和密码登录。

迁移完成后：

- 登录页只保留邮箱和密码登录，不再显示旧管理口令切换；
- 历史业务数据和原件不搬表、不复制、不删除；
- 目标账号成为历史工作区的管理员；
- 原临时账号、旧 Cookie 和静态口令不再能进入业务工作区；
- 其他工作区仍不能读取历史数据。

## 2. 非目标

- 不物理删除历史工作区或原始文件。
- 不把所有 `organization_id` 批量更新到新注册工作区。这会破坏复合外键、后台任务和历史平铺式原件路径。
- 不自动合并目标账号原工作区中已有的数据。
- 不把历史临时账号的全局平台管理员权限默认转授给目标账号。
- 不修改生产环境变量、部署脚本、Caddy、DNS 或服务器数据。

## 3. 用户流程

1. 用户先以已注册、已验证的正式账号登录。
2. 在账号设置中的一次性“接管历史工作区”操作中输入原管理口令。
3. 服务端先执行预检：目标账号必须是其当前工作区的唯一活跃管理员，且该工作区没有业务数据、其他活跃成员或未完成邀请。
4. 口令校验和预检通过后，服务端在一个数据库事务内完成接管，建立新的登录会话。
5. 用户会立即进入原有简历库，顶栏显示原注册工作区名称；旧管理口令登录入口消失且不能再使用。

目标邮箱只作为该次运行时请求的身份，不写入源码、迁移文件、测试固件、提交、PR 或应用日志。

## 4. 数据模型与安全边界

### 4.1 保留历史组织 ID

历史工作区的组织 ID 继续作为所有已有业务记录和历史平铺式原件的归属命名空间。只改变成员关系和有限的“当前用户拥有的私有状态”：

- 新账号新增一条历史工作区的活跃 `admin` 成员关系；
- 新账号原有的空工作区成员关系被停用，原组织标记为暂停但不删除；
- 历史占位成员关系和占位用户停用，并递增其会话版本；
- 历史工作区内 Agent 会话的 `owner_user_id` 改为目标账号，使接管后仍能读取自己的上下文；
- 未消费的邮箱 OAuth 授权意图、短期原件/导出访问授权全部撤销；
- 候选人数据、AI 结果、邮箱凭据、审计中的历史操作者字段均不改写。

平台审计表新增一条只含组织、用户 ID、成员关系 ID 和状态的事件，绝不写入候选人内容、原件路径、口令或邮箱明文。

### 4.2 接管状态

新增一条唯一的、控制面专用的 `legacy_workspace_adoptions` 记录。它保存来源组织、目标用户、目标成员关系、被停用的历史成员关系和接管时间，不保存口令、简历内容或邮箱明文。

该记录用于：

- 防止并发或重复接管；
- 让启动引导明确历史兼容身份已经退役；
- 让旧登录入口在接管完成后无法被重新启用。

### 4.3 安全的无上下文兜底

当前未显式绑定工作区的内部数据库 Session 会回落到历史工作区。历史工作区被真实用户接管后，这不再是安全兜底。

因此新增一个没有成员、没有候选人数据的固定系统兜底工作区。`organization_context_id()` 在没有显式上下文时只返回该空工作区。历史组织 ID 仍保留给历史原件兼容读取，不再作为未作用域查询的默认数据源。

## 5. 一次性授权与旧入口退役

接管 API 只接受已经登录的正式账号，并要求一次性提交原管理口令。该口令：

- 只在 HTTPS 请求体中校验，不进入日志、审计快照或数据库；
- 使用恒定时间比较；
- 复用服务端持久化登录限流，失败不会泄露历史工作区是否存在；
- 只在尚未接管时可用于此单一操作。

普通登录、会话恢复、文件下载、登出和邮箱 OAuth 回调均不再接受旧管理口令、`x-admin-token` 或旧布尔 Cookie。开发/测试中的 `allow_unauthenticated` 兼容固件保留，但不得成为生产 HTTP 认证回退。

## 6. 原子接管事务

事务中按固定顺序锁定历史组织、目标用户和两边成员关系：

1. 确认目标账号已验证、启用，且当前仅有一个活跃 `admin` 成员关系。
2. 确认目标原工作区为空，没有其他活跃成员和未完成邀请；否则失败并不修改任何记录。
3. 确认历史工作区尚未接管，且历史占位成员关系仍有效。
4. 使目标原工作区成员关系失效，并将该空组织标记为 `suspended`。
5. 创建目标账号在历史工作区中的唯一活跃 `admin` 成员关系，名称沿用目标原工作区名称。
6. 停用历史成员关系和占位用户，撤销其会话、OAuth 意图与短期文件访问授权。
7. 将历史工作区中属于占位用户的 Agent 会话归属转给目标账号。
8. 新建接管状态与平台审计记录，递增目标账号会话版本并返回新的三元身份会话。

任一步失败均回滚，不会出现一半数据在旧工作区、一半数据在新工作区的状态。

## 7. 前端体验

- `/login` 固定为工作邮箱和密码，不提供旧模式切换。
- 已登录目标账号且服务端仍允许接管时，在账户设置中显示简洁的一次性接管区。
- 区域明确说明：仅用于把历史数据接入当前账号，成功后不能撤销；不展示任何旧数据摘要。
- 提交期间按钮进入加载状态；错误只展示可操作的通用原因，例如“当前工作区已有内容，未执行接管”。
- 成功后刷新当前会话并进入已有工作台，不使用额外弹窗堆叠。

## 8. 验收与回归

- 正式账号接管后可读取原简历、原件、JD、邮箱配置和历史 Agent 对话。
- 其他工作区猜测资源 ID 时仍返回 `404`，无上下文 ORM 查询只能看到系统空兜底工作区。
- 原旧口令登录、`x-admin-token`、旧布尔 Cookie 和旧 OAuth 回调均不能访问业务数据。
- 接管后重启应用不会重新激活历史占位成员。
- 目标原工作区存在候选人、JD、邮箱、筛选器、评分、AI/Agent 记录、其他成员或邀请时，接管拒绝且不修改数据。
- 历史平铺式原件仍可按历史组织归属下载；新上传文件继续写入接管后的历史组织命名空间。
- 并发接管只有一个事务成功，重复请求返回稳定结果且不产生第二个活跃成员关系。
- 完整后端 `pytest`、Web `npm run build` 和登录路径 Playwright 回归通过。

## 9. 发布顺序

1. 合并包含 schema、接管服务、登录入口退役和回归测试的 PR。
2. 由发布负责人按生产发布流程先做数据库备份和迁移。
3. 用户使用目标正式账号完成一次性接管。
4. 验证登录、简历库、原件、JD、邮箱、Agent 与跨工作区访问边界。

本设计不授权任何 Agent 直接登录生产服务器、读取生产数据库或执行接管。
