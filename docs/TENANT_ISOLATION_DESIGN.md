# 用户注册、身份与工作区隔离设计

**状态：** 已批准，正在实现与验证
**目标分支：** `feature/tenant-isolation`
**范围：** 用户注册、用户身份、工作区（租户）隔离、试用期、成员角色、邀请与跨租户防护测试。

## 1. 背景与目标

当前系统使用单一管理口令保护一个共享数据空间。它不包含用户、工作区或成员身份，因此不能安全地开放自助注册。

本设计的目标是让每一个注册企业拥有独立工作区，并保证候选人、原始文件、JD、评分、邮箱配置、后台任务和 AI 上下文都只属于当前工作区。系统仍只向招聘人员提供辅助结论，不自动拒绝、录用或代表用户作出招聘决定。

### 1.1 本次交付

- 自助注册、登录、登出和会话恢复。
- 一个企业对应一个工作区；注册者自动成为该工作区管理员。
- 成员角色：`admin` 与 `recruiter`。
- 三档可配置套餐：基础版、进阶版、专业版。
- 可复制的邀请链接，供管理员邀请招聘官加入已有工作区。
- 密码重置令牌的签发与兑换能力；邮件投递采用可替换适配器。
- 注册后 30 个自然日的完整试用期。
- 全部租户业务数据、后台任务与新上传原件按工作区强制隔离。
- 跨租户越权、ID 猜测、Worker 与文件访问的自动化回归测试。

### 1.2 明确不在本次交付

- 支付、订阅扣款、发票或价格策略。试用到期后只显示续费提示，后续支付接入后再激活工作区。
- 多工作区切换。一个用户在本次仅属于一个工作区；数据模型可支持以后扩展。
- 自动发送招聘消息、自动拒绝或自动录用候选人。
- 生产部署、Caddy、Compose、DNS、域名或 `.env.production` 修改。

## 2. 账户与工作区模型

```text
UserAccount
  └── OrganizationMembership (role: admin | recruiter)
        └── Organization / Workspace
              └── 该工作区的候选人、简历、JD、评分、邮箱、任务与文件
```

### 2.1 新实体

| 实体 | 核心字段 | 说明 |
| --- | --- | --- |
| `organizations` | `id`、`name`、`plan_status`、`trial_started_at`、`trial_ends_at` | 一个企业的独立工作区；`plan_status` 初始为 `trial`。 |
| `product_plans` | `id`、`code`、名称、月价、试用天数、功能开关、启用状态、排序 | 平台可调整的套餐目录，不把价格和能力写死在前端。 |
| `users` | `id`、规范化唯一邮箱、姓名、密码哈希、启用状态 | 密码仅保存 scrypt 哈希和随机盐，不保存明文。 |
| `organization_memberships` | `organization_id`、`user_id`、`role`、启用状态 | 注册者为 `admin`；招聘官为 `recruiter`。 |
| `organization_invitations` | 工作区、受邀邮箱（可选）、令牌摘要、角色、失效/接受时间 | 仅管理员可创建；原始邀请令牌只在创建时返回一次。 |
| `password_reset_tokens` | 用户、令牌摘要、失效/使用时间 | 只保存摘要；请求接口始终返回同一成功文案，避免枚举邮箱。 |

`organizations` 通过 `plan_id` 指向当前套餐；`plan_status` 表示试用、已激活、已过期或暂停等访问状态。套餐本身与工作区状态分离，便于后续接入支付和人工调整。

### 2.2 角色权限

| 能力 | admin | recruiter |
| --- | --- | --- |
| 查看、上传、筛选候选人，评分、总结、JD 匹配、Agent | 是 | 是 |
| 查看工作区与试用状态 | 是 | 是 |
| 配置收件邮箱 | 是 | 否 |
| 创建/撤销邀请、管理成员 | 是 | 否 |
| 未来账单与续费 | 是 | 否 |

平台管理员不是普通企业角色。它仅用于运营套餐目录、调整企业套餐和处理试用状态；正常注册用户永远不能把自己的工作区切到更高档位。

### 2.3 三档套餐与可调节项

| 套餐 | 初始能力边界 | 可调整项 |
| --- | --- | --- |
| 基础版 | 简历库、筛选、评分、总结、JD 匹配、招聘 Agent | 价格、试用天数、功能开关、展示顺序、是否对新注册开放。 |
| 进阶版 | 基础版加收件邮箱、AI-JD | 同上。 |
| 专业版 | 进阶版加面试题、面试记录与 HRBP 参考 | 同上；C 阶段功能未实现前不会假装开放。 |

每个套餐的功能开关以服务端 `feature_flags` 保存，例如 `mailbox_import`、`ai_jd_generation`、`interview_questions`、`hrbp_reference`。每个受限 API 在后端检查当前工作区套餐，前端只负责展示，不承担授权判断。

初始默认策略：新注册工作区进入 30 天的 **进阶版试用**，使当前已实现的 A、B 能力可完整体验；专业版功能会在 C 阶段真实实现后再开放。平台管理员可在不改代码的情况下调整默认试用档位和时长。

### 2.4 试用状态

- 注册成功时，`trial_started_at` 为服务端当前时间，`trial_ends_at` 为其后 30 天。
- 试用有效期间拥有完整产品能力。
- 试用到期后仍可登录到期提示页，但业务 API 返回稳定错误 `trial_expired`，不返回候选人、原件或 AI 结论，也不触发新的模型任务。
- 数据保留，不删除简历或历史记录；后续支付完成后可将 `plan_status` 激活。

## 3. 身份与 API 设计

### 3.1 会话

服务端 Session Cookie 只保存：

```json
{
  "user_id": "...",
  "organization_id": "...",
  "membership_id": "..."
}
```

每个受保护请求都会重新验证用户、成员关系、工作区状态和试用期，不信任浏览器传来的工作区 ID。

### 3.2 认证接口

| 接口 | 请求 | 结果 |
| --- | --- | --- |
| `POST /v1/auth/register` | 企业名称、姓名、邮箱、密码 | 创建用户、工作区、管理员成员关系与 30 天试用会话。 |
| `POST /v1/auth/login` | 邮箱、密码 | 建立当前工作区会话。 |
| `GET /v1/auth/session` | 无 | 返回认证、角色、工作区名称、试用状态和到期时间。 |
| `POST /v1/auth/logout` | 无 | 清除会话。 |
| `POST /v1/auth/password-reset/request` | 邮箱 | 始终返回通用成功结果；签发一次性令牌并委托邮件适配器投递。 |
| `POST /v1/auth/password-reset/complete` | 令牌、新密码 | 仅可使用未过期的一次性令牌。 |
| `POST /v1/organization/invitations` | 角色、受邀邮箱（可选） | 管理员创建邀请链接。 |
| `POST /v1/auth/invitations/accept` | 邀请令牌、姓名、邮箱、密码 | 加入指定工作区，角色受邀请限制。 |
| `GET /v1/organization/plan` | 无 | 当前成员查看工作区套餐、试用状态和可用能力。 |
| 平台管理套餐接口 | 仅平台管理员 | 调整三档名称、价格、功能、试用期、启用状态和企业当前档位。 |

密码重置邮件不能把令牌写入日志或 API 响应。若尚未配置邮件投递适配器，生产 UI 必须明确提示“请联系管理员重置”，不能假装邮件已经发送。

### 3.3 兼容入口

- 主入口 `https://hr.greatsellai.net` 直接承载工作台、`/v1`、`/health`、`/login`、`/register` 与 `/forgot-password`。
- `https://greatsellai.net/greatsellhr/` 是可选兼容入口，使用 `/greatsellhr/v1` 与 `/greatsellhr/health`；它只能由官网自身的边缘代理转发到 HR 主站，不能要求或导致 `greatsellai.net/` 根域映射到 HR 服务器。
- 前端根据当前入口选择 API 前缀，主入口始终使用同源 `/v1`。

## 4. 数据与文件隔离

### 4.1 工作区归属列

以下可被 API 直接读取、写入或由 Worker 扫描的业务根记录必须具有非空 `organization_id` 与索引：

- `candidates`、`resumes`、`resume_upload_idempotency_keys`、`resume_ai_extraction_jobs`、`resume_fact_snapshots`；
- `saved_filters`；
- `score_templates`、`resume_scores`、`resume_summaries`；
- `jobs`、`job_versions`、`job_matches`、`job_match_batches`、`job_match_batch_items`；
- `mailbox_configs`、`email_attachment_imports`。

教育、经历、技能、原文块、JD 条款和评分维度等子记录通过已经受工作区过滤的父 `Resume`、`Job` 或 `ScoreTemplate` 访问。它们不会暴露为绕过父级的独立 API 资源。

现有唯一约束会改为工作区范围，例如筛选器名称、评分模板名称和上传幂等键不能跨工作区冲突。

### 4.2 强制过滤机制

1. 所有上述模型继承 `OrganizationScoped`。
2. 身份依赖把服务端验证得到的 `organization_id` 写入当前 SQLAlchemy Session 上下文。
3. SQLAlchemy 全局 loader criteria 对该 Session 内所有 ORM 查询自动增加 `organization_id = 当前工作区`。
4. `before_flush` 守卫为新建的工作区记录填入当前工作区，并拒绝任何跨工作区写入或篡改归属列。
5. 通过猜测其他工作区 ID 访问资源时一律返回 `404`，不泄露资源是否存在。

这套机制是默认防线，不依赖每个开发者手工记住过滤条件；关键直接 ID 查询仍会保留显式归属断言作为纵深防御。

### 4.3 原件存储

新上传的文件保存为：

```text
uploads/<organization_id>/<random-id>.<extension>
```

原件读取先验证当前工作区拥有对应 `Resume`，再解析限定在当前工作区目录下的 storage key。路径遍历、其他工作区目录和猜测 storage key 均拒绝。

迁移前的平铺文件不移动，也不触及生产卷；它们只归入 `legacy` 工作区并继续由数据库归属校验保护。所有新文件使用分工作区目录。

## 5. Worker、AI 与邮箱隔离

### 5.1 AI 提取

- API 入队时，任务继承 Resume 的 `organization_id`。
- Worker 可以全局领取队列项，但领取后立刻从任务恢复工作区上下文，再读取简历、原文块和写入事实。
- 任务完成前再次校验 Resume、事实快照与任务属于同一工作区；不匹配即失败且不写入。

### 5.2 JD 批量匹配

- 批次、批次项、JD 版本和 Resume 快照必须具有同一 `organization_id`。
- Worker 领取批次项后恢复工作区上下文；任何跨工作区组合都以稳定错误失败。

### 5.3 邮箱同步

- 每个 `MailboxConfig` 仅属于一个工作区。
- Worker 全局选择到期配置后，以配置的工作区上下文同步；创建候选人、简历、附件导入审计和 AI 任务均继承该工作区。
- 邮箱凭据继续保持服务端加密且不回显。

### 5.4 招聘 Agent

Agent 只能使用当前请求 Session 绑定的工作区查询。模型输入不包含其他工作区的候选人、JD、评分或邮件元数据；工具调用产生的 ID 也会再次受工作区过滤。

## 6. 旧数据迁移与兼容性

Alembic 迁移不读取环境变量、不读取文件卷、不读取候选人内容：

1. 创建 `legacy` 工作区、对应内部兼容管理员用户和管理员成员关系。
2. 为已有业务根记录回填 `legacy` 工作区 ID。
3. 将新增列改为非空并创建外键、索引与工作区范围唯一约束。
4. 保留现有全局管理口令作为仅限 `legacy` 工作区的兼容登录回退，直到原管理员创建正式邮箱账号后再移除。
5. 初始化基础、进阶、专业三档套餐，并将 legacy 工作区绑定到可由平台管理员后续调整的套餐。

迁移只改数据库结构与归属元数据，不复制、导出、移动或删除 PDF、数据库数据、环境变量或密钥。

## 7. 前端体验

- `/login`：邮箱密码登录，保留旧管理口令兼容说明但不暴露系统细节。
- `/register`：企业名称、姓名、邮箱、密码、试用期限说明，注册成功直接进入工作台。
- `/forgot-password`：通用请求确认，不枚举邮箱；邮件适配器未启用时提供明确支持路径。
- 兼容入口存在时，以上路由可在 `/greatsellhr/` 前缀下继续使用。
- 顶栏展示当前工作区名称、角色和剩余试用天数；到期时显示阻断式续费提示。
- 注册/登录页面沿用现有深墨、灰、品牌红和高信息密度产品语言，不把占位官网改造成 HR 工作台。
- 工作区管理员能看到当前套餐、试用剩余时间与升级说明；不能自己变更档位。
- 平台管理页后续提供套餐与企业套餐调整入口，不对普通租户暴露。

## 8. 测试与验收

### 8.1 身份与试用

- 注册后创建独立工作区、管理员成员关系和准确的 30 天到期时间。
- 正确/错误密码、禁用成员、过期邀请、已使用重置令牌和邮箱枚举防护均有覆盖。
- 试用到期后业务 API 返回 `trial_expired`，不创建任务、不调用模型。
- 三档套餐功能开关必须由后端执行：基础版不能调用邮箱或 AI-JD 接口；专业版未实现能力不能被错误宣称为可用；企业管理员不能自行修改套餐。

### 8.2 跨工作区越权

使用两个独立 TestClient 注册工作区 A 与 B，并断言：

- A 无法通过 Resume、Candidate、Score、Summary、Job、JobVersion、Match、Batch、Mailbox 配置或导入记录 ID 读取/修改 B 的数据；返回 `404`。
- A 的搜索、简历库、筛选器、评分模板、JD 列表、Agent 排名不包含 B 数据。
- A 无法下载 B 的原件，也不能通过伪造 storage key 访问 B 目录。
- A 的 AI 提取、JD 批次和邮箱同步写入只保留在 A；Worker 处理 B 任务时不污染 A。
- 工作区范围唯一约束允许 A、B 使用同名模板/筛选器和同一客户端幂等键。

### 8.3 迁移与回归

- 从最新旧 schema 升级后，既有业务记录全部归入 legacy 工作区。
- 旧管理口令仍只能进入 legacy 工作区。
- 后端完整 pytest、前端 `npm run build`、迁移升级/降级检查和 `git diff --check` 必须通过。

## 9. 实施顺序与提交边界

1. **设计提交（当前）**：本文件，零业务代码改动。
2. **身份、套餐与 schema 提交**：模型、Alembic、密码哈希、注册/登录/会话、三档套餐、legacy 兼容。
3. **隔离执行提交**：全局 Session 范围、服务、Worker、邮箱、Agent 与文件目录边界。
4. **前端提交**：注册、登录、找回密码、试用状态与兼容入口 API 前缀。
5. **安全回归提交**：跨工作区测试、迁移测试、构建与验收文档。

每一步均从 `main` 基线派生，先检查 diff、提交到功能分支、推送 GitHub，再继续下一步。不会直接推送 `main` 或部署生产。

## 10. 评审结论请求

请确认以下默认决策后再开始业务实现：

1. 每个注册企业获得独立工作区，注册者为管理员。
2. 试用期为注册后 30 个自然日，到期后锁定业务数据访问并保留数据。
3. 本期只支持一个用户属于一个工作区，成员邀请用于加入现有工作区。
4. 密码重置令牌逻辑本期完成；正式邮件投递需要后续提供邮件服务配置，未配置时不伪造发送成功。
5. 新注册默认获得 30 天进阶版试用；基础、进阶、专业三档由平台管理员可配置，普通企业管理员不能自行升级。
